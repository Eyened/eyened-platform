Images are stored under a **storage backend** and registered in the database as `Project → Patient → Study → Series → ImageInstance → ImageStorage`. Each import supplies one flat record per image (`ImportRow`).

| Method | Best for |
|--------|----------|
| [REST API](#rest-api) | Integrations, one-off uploads, scripts using HTTP |
| [ORM importer](/eyened-platform/orm/importer) | Bulk imports, CSV, plan → review → apply, metadata patches |

Field names and types for patient, study, series, and image metadata are listed in [Import metadata fields](/eyened-platform/import_metadata_fields).

## REST API

`POST /api/import/image` accepts a JSON body with `data` (one `ImportRow`) and `options`:

```json
{
  "data": {
    "project_name": "my-project",
    "patient_identifier": "Patient_1",
    "study_date": "2023-05-15",
    "storage_backend_key": "local",
    "object_key": "path/to/image.jpg",
    "modality": "ColorFundus",
    "laterality": "R"
  },
  "options": {
    "include_stack_trace": false
  }
}
```

**File location:** set `storage_backend_key` and `object_key` (path within that backend). The server resolves files via configured storage mounts (`EYENED_STORAGE_MOUNTS`), not a single global `IMAGES_BASEPATH` field on the payload.

**Hierarchy:** provide lookup fields (`project_name`, `patient_identifier`, `study_date`, `series_instance_uid`, …) or primary keys (`project_id`, `patient_id`, …). Missing parents are created when the row supplies enough keys to identify them; existing rows are matched and reused.

**Typical required fields:** `project_name`, `storage_backend_key`, `object_key`, and `modality` (needed by the viewer). Device defaults (`manufacturer`, `manufacturer_model_name`, …) may be required unless your deployment fills them server-side — see the [ORM importer](/eyened-platform/orm/importer) `defaults` example.

**Options:** only `include_stack_trace` (default `false`) — when `true`, failed imports return a stack trace in the response.

Authenticate first (session cookie), then call the endpoint. Example workflow: [import_api.ipynb](https://github.com/Eyened/eyened-platform/blob/main/notebooks/import_api.ipynb) (uses `ImageImporter` from `eyened_orm.importer.image_importer`).

:::caution
`ImageImporter` still sends legacy `create_*` flags in `options`, but the API ignores them. Creation is driven by the row content and the shared ORM planner.
:::

## ORM importer

For batch work, use `plan_image_import` → review (`run.display_summary()`) → `run.apply()` → `session.commit()`. Optional JSON export supports audit and undo.

Full guide: **[ORM Importer](/eyened-platform/orm/importer)**.
