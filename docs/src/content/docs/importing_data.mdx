Before images appear in the viewer, they must be **registered in the database** and linked to a file on a **storage backend** (local disk, S3, etc.). Importing creates this link and attaches metadata — patient, study, series, modality, laterality, and so on.

Each import supplies one flat record per image (`ImportRow`). The platform builds the hierarchy:

`Project → Patient → Study → Series → ImageInstance → ImageStorage`

Existing records are matched and reused, so you can attach new images to existing patients, studies, or series.

Field names and types are listed in [Import metadata fields](/eyened-platform/import_metadata_fields).

## ORM importer

The **ORM importer** is the primary way to load data. Use it from Python or the `eorm` CLI for bulk imports, CSV files, and metadata patches.

Typical workflow:

1. Build `ImportRow` objects (or load from CSV)
2. Optionally enable [row preparation](/eyened-platform/orm/importer#row-preparation) (`PreparationOptions`) — e.g. `infer_metadata_from_dicom_header` for PatientID/StudyDate/modality/resolutions, or `link_oct_enface_series` to co-locate OCT–enface
3. Optionally [export prepared rows to CSV](/eyened-platform/orm/importer#export-prepared--inferred-metadata-to-csv) to verify inferred metadata (`build_image_import_rows` → `write_import_rows_csv` → `plan_import`)
4. `plan_image_import(session, rows, ...)` — or `plan_import` on already-prepared rows — preview what will be created or matched
5. `run.display_summary()` — review the plan
6. `run.apply()` then `session.commit()` — write to the database
7. Optionally export the run to JSON for audit or undo

Each row points to an image file via `storage_backend_key` and **relative** `object_key` within that backend. The file must already exist — import registers the path in the database; it does not copy or upload image bytes. Place files on the backend first, then run the import. DICOM header reading uses `EYENED_STORAGE_MOUNTS[backend] / object_key` (or a custom `raw_loader`).

Full guide: **[ORM Importer](/eyened-platform/orm/importer)** (requires **[ORM setup](/eyened-platform/orm/getting_started)**).

## Thumbnails

Import does **not** generate thumbnails. After images are registered, generate them separately — see [Thumbnails](/eyened-platform/thumbnails):

- **`eorm update-thumbnails`** — backfill missing thumbnails from the shell
- **`PostImport`** — run after `run.apply()` for newly imported instances
- **`POST /api/import/update_thumbnails`** — queue a background job (requires an RQ worker on the `default` queue)

## REST API (alternative)

For integrations that cannot run the ORM directly, `POST /api/import/image` accepts the same `ImportRow` fields over HTTP:

```json
{
  "data": {
    "project_name": "my-project",
    "patient_identifier": "Patient_1",
    "study_date": "2023-05-15",
    "storage_backend_key": "local",
    "object_key": "path/to/image.jpg",
    "modality": "ColorFundus",
    "laterality": "R"
  },
  "options": {
    "include_stack_trace": false
  }
}
```

The API has the same limitation as the ORM importer: **it registers an existing file, it does not upload one.** The image must already be on the storage backend and reachable at `object_key`. There is no multipart upload endpoint — if you need to get files onto the backend, do that separately (filesystem copy, S3 upload, etc.) and then call the API to register them.

Authenticate first (session login or `Authorization: Bearer` token). Example notebook: [import_api.ipynb](https://github.com/Eyened/eyened-platform/blob/main/notebooks/import_api.ipynb).

For batch work, plan/review workflows, CSV, and undo, prefer the [ORM importer](/eyened-platform/orm/importer).
