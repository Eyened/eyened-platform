To access the Eyened platform, users need to authenticate. See below for options on how to manage them.

Moving an existing site to SSO? Follow [Switching to SSO](/eyened-platform/guides/switching_to_sso).

## Standalone / database backend

By default, accounts are managed in the MySQL database holding all Eyened data. The database table `creator` holds usernames, password hashes and a few other fields describing users. To create a new user, use the ORM command `eorm create-user`. More advanced user management is done by accessing the `Creator` table in the database using SQL.

## OpenID Connect (OIDC)

It's also possible to integrate with an existing authentication backend in an organization using [OpenID Connect](https://openid.net/developers/discover-openid-and-openid-connect/) (or "OIDC" for short). This allows you to use the single sign-on flow that users within your organization are already used to. Users won't have to remember a separate password for the Eyened platform. Upon sign-in, the browser of the user is redirected to the authorization page at the OpenID Connect provider, and then redirected back to the Eyened platform.

To set this up, a few steps need to be taken care of.

### OIDC application registration

At the party that manages the central authentication system, you need to request an App registration for OpenID Connect authentication. The application uses the "auth code flow for web applications" and requires the return of an "ID Token" from the token endpoint. The specific values that you'll need to provide depend on the system in use, but in general you'll only need to provide a "Redirect URL" sometimes also named "Callback URL". See the [`EYENED_OIDC_REDIRECT_URL`](#EYENED_OIDC_REDIRECT_URL) configuration option for details on the correct value for this URL.

You'll receive some configuration values from your provider, that need to be set up in the Eyened application.

### OIDC Setup

To configure OIDC authentication in Eyened, you need to set up at least the `Client ID`, `Client Secret`, `Metadata URL`, `Redirect URL`. You also need to enable OIDC authentication (`EYENED_API_AUTH_OIDC_ENABLED=true`).

After configuration, you can test if it works. Errors will be visible in the logs of the Eyened server. Also, the response from the authentication endpoint that is called from the callback in the frontend can be helpful. Use your browser dev tools for that.

:::tip
Try to do the initial setup in your local development environment. Ask the provider to configure the redirect URL `http://localhost:8080/users/oidc-callback` for you.
:::

### SURFconext

1. Request an OIDC connection from SURFconext, with redirect URL `https://eyened.example.org/users/oidc-callback` (your own host). Ask SURFconext to release the `email` and `schac_home_organization` attributes, and for the `schac_home_organization` value of each institution you want to admit.
2. Set these in `deploy/.env`, with the client id and secret SURFconext issued. For the SURFconext test connection, use `https://connect.test.surfconext.nl/.well-known/openid-configuration` as the metadata URL.

   ```bash
   EYENED_API_AUTH_OIDC_ENABLED=true
   EYENED_OIDC_CLIENT_ID=<client id>
   EYENED_OIDC_CLIENT_SECRET=<from-surfconext>
   EYENED_OIDC_METADATA_URL=https://connect.surfconext.nl/.well-known/openid-configuration
   EYENED_OIDC_REDIRECT_URL=https://eyened.example.org/users/oidc-callback
   EYENED_OIDC_CREATE_NEW_ACCOUNTS=true
   EYENED_OIDC_ALLOWED_HOME_ORGANIZATIONS=erasmusmc.nl
   EYENED_OIDC_PROVIDER_NAME=SURFconext
   ```

3. Run `docker compose up -d` from `deploy/`.
4. A first login creates the Account with no project access. On the Account's admin page, choose **Add to project** and pick a role; see [Access control](/eyened-platform/guides/access_control).

:::note
SURFconext has no single logout. Logging out of Eyened ends the Eyened session only, so a later login can skip the institution's login page.
:::

:::caution
With `EYENED_OIDC_ALLOWED_HOME_ORGANIZATIONS` set, a login that carries no `schac_home_organization` is refused with 403. eduID logins may not carry it.
:::

### Link an existing Account to SSO

Use this when a person already has an Account, for example a password Account, and should keep it when they switch to SSO. To move a whole site, follow [Switching to SSO](/eyened-platform/guides/switching_to_sso).

1. In **Admin**, open the person's Account.
2. Choose **Link email** and enter the email address exactly as the provider sends it. The match is case-sensitive.
3. The person logs in with SSO. Their first login with that email lands in this Account and pins it to their SSO identity. From then on the email is no longer used.

The **SSO email** line on the Account's admin page shows *Not linked*, the linked email, or *Signed in with SSO* once the Account is pinned.

- An email already linked to another Account is refused.
- Linking again replaces the link, including the pin. The old SSO login stops matching until the person logs in with the new email.
- If the email does not match, for example because of a case difference, the login does not reach this Account. With `EYENED_OIDC_CREATE_NEW_ACCOUNTS=true` the person gets a new, empty Account named by their email instead, or 409 if an Account already has that name. Otherwise the login is refused.

Linked Accounts keep their project memberships.

### OIDC Configuration

The OIDC backend is configured in the same way as the ORM, through env variables. See the [ORM documentation](/eyened-platform/orm/configuration) on how to provide these.

This is a list of all available configuration options. Further down, more details are available.

| Option                                   | Description                              |
|------------------------------------------|------------------------------------------|
| EYENED_OIDC_CLIENT_ID                    | Application Client ID                    |
| EYENED_OIDC_CLIENT_SECRET                | Application Client Secret                |
| EYENED_OIDC_METADATA_URL                 | Application Metadata URL                 |
| EYENED_OIDC_REDIRECT_URL                 | Redirect URL in the Eyened platform      |
| EYENED_OIDC_PROVIDER_NAME                | Friendly name of the OIDC provider       |
| EYENED_OIDC_ADDITIONAL_TOKEN_VALIDATIONS | Additional token validations             |
| EYENED_OIDC_CREATE_NEW_ACCOUNTS          | Enable creation of new accounts for OIDC |
| EYENED_OIDC_ALLOWED_HOME_ORGANIZATIONS   | Institutions allowed to log in           |
| EYENED_API_AUTH_OIDC_ENABLED             | Enable OIDC authentication               |
| EYENED_API_AUTH_PASSWORD_ENABLED         | Enable password authentication           |

#### `EYENED_OIDC_CLIENT_ID`, `EYENED_OIDC_CLIENT_SECRET`, `EYENED_OIDC_METADATA_URL`

- Required: yes
- Default values: -

You should have received the Application `Client ID` (usually a string of random characters and numbers), `Client Secret` (another string of random characters and numbers) and `Metadata URL` (an URL) in response to your request for an App registration. The `Metadata URL` should end with `/.well-known/openid-configuration`, and should be publicly accessible.

If you only received an "Issuer URL" or similar, the correct URL usually is `https://[Issuer URL]/.well-known/openid-configuration`. Check the documentation of the authentication provider, or ask the issuing party for assistance.

#### `EYENED_OIDC_REDIRECT_URL`

- Required: yes
- Default value: -

This is the `Redirect URL` that you supplied during App registration. This is the URL where the OIDC provider redirects the browser after authentication. The correct value for the URL is `https://eyened.example.org/users/oidc-callback`, where you need to replace `eyened.example.org` with the actual domain where the Eyened platform for your organization is running. You can visit this URL yourself in your deployed Eyened application, it will display a simple error message.

#### `EYENED_OIDC_PROVIDER_NAME`

- Required: no
- Default value: `OpenID Connect`

At the Eyened login screen, access to the OIDC authentication will be visible through a button with the text *Login with \[...\]*. Set this configuration option to the name of your login system to replace the default value with the name that your users know, e.g. "SURFconext" or "ACME Single Sign-on".

#### `EYENED_OIDC_ADDITIONAL_TOKEN_VALIDATIONS`

- Required: no
- Default value: -

You can use this configuration option to list additional claims that a login must hold. They are checked against the ID token and userinfo claims together. The server already checks the "Issuer" (`iss`), "Audience" and timing claims itself, so you don't need to list `iss`. Specific providers might advise to validate claims specific to their implementation. E.g. [MS Entra advises](https://learn.microsoft.com/en-us/entra/identity-platform/claims-validation) to also check the "Tenant" claim (`tid`).

Example: the configuration value `tid=12345,foo=bar` will validate the "Tenant" claim (`tid`) to be `12345`, and the made-up `foo` claim to have value `bar`. A list claim passes if it contains the value. Separate key and value from each other using an equals sign (`=`), multiple key-value sets are separated by a comma (`,`).

#### `EYENED_OIDC_CREATE_NEW_ACCOUNTS`

- Required: no
- Default value: `false`

Whether to create new accounts for users that have authenticated successfully using OIDC, but are unknown to the Eyened application. Read [OIDC Access control](#oidc-access-control) below for details.

#### `EYENED_OIDC_ALLOWED_HOME_ORGANIZATIONS`

- Required: no
- Default value: -

A comma-separated list of `schac_home_organization` values allowed to log in through OIDC, e.g. `erasmusmc.nl,uu.nl`. Ask your provider for each institution's value. A login from any other institution, or one without the claim, is refused with 403. Empty admits every institution.

#### `EYENED_API_AUTH_OIDC_ENABLED`

- Required: no
- Default value: `false`

When configuring authentication options, this option enables OIDC authentication. It will display the *Login with \[...\]* button on the login screen, named by [`EYENED_OIDC_PROVIDER_NAME`](#eyened_oidc_provider_name).

#### `EYENED_API_AUTH_PASSWORD_ENABLED`

- Required: no
- Default value: `true`

When configuring authentication options, this option controls password authentication. When enabled, the username + password dialog is shown in the login screen. When `false`, the dialog is hidden and the server refuses password logins and sign-ups.

After enabling OIDC authentication, you probably want to disable the default password authentication, which you can do by setting this option to `false`. Link every existing Account first; see [Switching to SSO](/eyened-platform/guides/switching_to_sso). In the rare case that you want to keep multiple authentication options available at the same time, just set both options to `true`.


### OIDC Access control

To manage who actually has access to the Eyened platform using OIDC, there are two possible approaches: either you control access inside the Eyened application itself, or at the OIDC provider. This is controlled using the `EYENED_OIDC_CREATE_NEW_ACCOUNTS` configuration key.

#### Inside the Eyened application

This is the default operation mode, when `EYENED_OIDC_CREATE_NEW_ACCOUNTS=false`.

If you decide to keep access control in the Eyened application itself, only users who have an existing account in the Eyened platform (in the `creator` table) are allowed to log in. When adding a new account, you need to link the account to identities received from OIDC. To do this, you'll need to provide a claim available in received ID tokens. For security reasons, the "Subject" claim should be used in the long term, but this claim usually holds some random identifier that you cannot predict up front.

To resolve this, the `email` claim serves as a temporary link. **Link email** stores `oidc:email:<address>` in `creator.EmployeeIdentifier`. After the first successful login, the value is replaced with the "Subject" claim (prefix `oidc:sub:`). The link and that replacement each write an audit row. See [Link an existing Account to SSO](#link-an-existing-account-to-sso) for the steps.

:::tip
If you're migrating from password authentication to OIDC, link an email to each existing Account. Users can then sign in with both. When you're sure they reach the same Account through OIDC, disable password authentication.
:::

#### At the OIDC provider

This mode is activated when you set `EYENED_OIDC_CREATE_NEW_ACCOUNTS=true`.

If you handle access control at the OIDC provider, the provider usually allows a way to control which persons are authorized to access the application. Maybe you're connected to your organizations' Active Directory, and you can control access using Groups in AD. This totally depends on the provider, and your organization. Optionally consult your IT department for possibilities.

When enabled, the Eyened platform accepts every OIDC login that passes [`EYENED_OIDC_ALLOWED_HOME_ORGANIZATIONS`](#eyened_oidc_allowed_home_organizations) and [`EYENED_OIDC_ADDITIONAL_TOKEN_VALIDATIONS`](#eyened_oidc_additional_token_validations). For new accounts, an entry in the `creator` table will be added and linked to their OIDC identity (by recording the "Subject" claim in the `creator.EmployeeIdentifier` field). When creating a new account, the other fields populated in the `creator` table are `CreatorName` (the full `email` claim) and `PasswordHash` (set to an unusable password, so the user cannot log in using password authentication). A first login with no `email` claim, or an email address over 45 characters, is refused with 400 and no account is created.

:::tip
Only the value in the `creator.EmployeeIdentifier` field matters for OIDC authentication. Feel free to adjust the name in `creator.CreatorName` to whatever is convenient for displaying in the Eyened frontend. Logins never change `creator.CreatorName`; only account creation sets it.
:::

## Locking an account out

`eorm deactivate --user U` refuses the account at scope resolution: it cannot log in, cannot refresh a token, and every route that reads or writes project data closes to it on its **next request**, even with a valid token. Memberships are kept, so `eorm reactivate` restores exactly what it had. A `Creator` row is never deleted — deactivation is the retirement path.

Two limits are worth knowing:

- **It is not instantaneous for `GET /api/auth/me`.** That route resolves the token without re-reading the account's status, so an unexpired access token the user already holds still returns their own account details until it expires on its own schedule. One other authenticated route answers the same way — `GET /api/import/status/{task_id}`, which reports a queued job's bare status and carries no project data. Everything that reads or writes project data resolves the scope fresh and closes.
- **It is not absolute against OIDC.** A deactivated password-only account has `EmployeeIdentifier = NULL`, which no OIDC login matches, so with `EYENED_OIDC_CREATE_NEW_ACCOUNTS=true` the same person can sign in through the provider under a different username and receive a **new** account. That new account holds no memberships, so it reaches no project data until someone grants it; an exact username match is refused with 409 rather than linked.

To force re-authentication across the board, set a new `EYENED_API_SECRET_KEY` — this invalidates every outstanding token, including refresh tokens (default lifetime: 7 days).

## Access is separate from authentication

Signing in successfully grants nothing on its own. What a user can see comes from their project memberships, so an account created here — by `eorm create-user`, by self-registration, or by OIDC auto-provisioning — sees an **empty platform** until it is granted a role.

See **[Access control](/eyened-platform/guides/access_control)** for the model, and **[CLI reference — Users and access](/eyened-platform/orm/cli#users-and-access)** for the commands.

## Password policy

A new password must be at least 15 characters (maximum 128) and must not contain your username or the word `eyened`, in any capitalisation. There are no composition rules — no required digits, cases or symbols.

The policy applies wherever a password is set — `eorm create-user`, `eorm set-password`, `eorm init-admin`, `POST /api/auth/register`, `POST /api/auth/change-password` — and never at login, so existing passwords keep working until they are changed.
