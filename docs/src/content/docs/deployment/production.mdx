## Before you start

Docker with **Compose 2.26 or newer**, and a checkout of the repository — images are built from
it, so the checkout *is* the version you run.

## First run

```bash
git clone https://github.com/Eyened/eyened-platform.git
cd eyened-platform/deploy
cp .env.example .env && chmod 600 .env
```

`.env` holds five secrets, so restrict it before you fill it — `cp` preserves the example file's
permissions, which are world-readable.

Fill four of them with `openssl rand -hex 32`: `EYENED_API_SECRET_KEY`, `EYENED_REDIS_PASSWORD`,
`MYSQL_ROOT_PASSWORD` and `EYENED_DATABASE_PASSWORD`. Compose refuses to start while any of the
four is empty. The fifth, `EYENED_API_ADMIN_PASSWORD`, is a password you will type at the login
screen — compose starts without it, and `init` (see [what happens on every
`up`](/eyened-platform/deployment/operations#what-happens-on-every-up)) fails on an empty
database, where it creates the first administrator.

Set `HTTP_PORT` to the port you want to serve on, then:

```bash
docker compose up -d --build
```

Open `http://<host>:<HTTP_PORT>` and sign in as `EYENED_API_ADMIN_USERNAME` (default `admin`).

## Using an external database

Remove `local-db` from `COMPOSE_PROFILES` and set `EYENED_DATABASE_HOST`, `_PORT`, `_USER`,
`_PASSWORD` and `_DATABASE`. The account needs DDL rights, because migrations run as it.

`MYSQL_ROOT_PASSWORD` must still be set to something non-empty even though no bundled database
runs: compose interpolates variables for profile-disabled services too, and refuses to start
without it.

## Behind a TLS-terminating proxy

The stack speaks plain HTTP on `HTTP_PORT`. To serve it over HTTPS, terminate TLS in front of it
and proxy to that port.

Forward `X-Forwarded-Proto`. The bundled nginx prefers an inbound value over its own scheme —
`deploy/nginx/default.conf.template` maps `$http_x_forwarded_proto` to `$client_scheme` and
passes that upstream — so the application sees `https` rather than the `http` of the inner hop.

**There is no platform-wide public-origin setting.** `PUBLIC_HOST` and `PUBLIC_URL` in
`.env.example` apply *only* to the bundled Keycloak layer (`compose.oidc.yaml`); nothing else
reads them, and setting them on a production stack has no effect.

With OIDC, set `EYENED_OIDC_REDIRECT_URL` to the public `https` URL — see
[Authentication](/eyened-platform/guides/authentication). Registering it with the provider is
part of that page, not this one.

:::caution
This topology has not been exercised end to end. `deploy/keycloak/README.md` records the same
for the bundled-Keycloak case.
:::

## Before you go live

- `EYENED_API_PUBLIC_AUTH_DISABLED=false` — `true` skips the login screen entirely and runs every
  request as the administrator.
- `EYENED_API_DEBUG=false`.
- `chmod 600 .env` — it holds five secrets, and anyone who can read `EYENED_API_SECRET_KEY` can
  forge an administrator token.
- Secrets generated for *this* deployment. Never copy them between stacks.
- Backups configured before you have data worth losing — see
  [Operations](/eyened-platform/deployment/operations#routine-backups).

## Sizing

One rule: `WORKERS` × (`EYENED_API_POOL_SIZE` + `EYENED_API_MAX_OVERFLOW`) must stay under the
database's `max_connections`. At the shipped defaults that is 4 × (16 + 4) = 80. MySQL's default
`max_connections` is 151 and this stack does not override it, so the defaults fit — but confirm
the value on an external database server before raising any of them.

A startup validator refuses to boot the server if `EYENED_API_THREADPOOL_LIMIT` exceeds
`EYENED_API_POOL_SIZE` + `EYENED_API_MAX_OVERFLOW`. For why these are sized the way they are, see
[Platform design](/eyened-platform/platform_design).

## Image datasets

Each dataset is mounted read-only at `/data/<key>`, where `<key>` is its `StorageBackend.Key`.

1. `cp compose.storage.example.yaml compose.storage.yaml`, and list each dataset as
   `- /host/path:/data/<key>:ro`.
2. With `:compose.workers.yaml` also in `COMPOSE_FILE`, uncomment the worker entries in
   `compose.storage.yaml`. Workers read the datasets directly, so without their mounts every
   thumbnail and inference job fails; a worker now refuses to start rather than fail silently.
3. In `.env`, append `:compose.storage.yaml` to `COMPOSE_FILE` and set
   `EYENED_STORAGE_MOUNTS={"<key>":"/data/<key>"}`, one entry per dataset.
4. `docker compose up -d`.

Platform storage (thumbnails, segmentations) is a Docker volume unless `PLATFORM_STORAGE_PATH`
names a host path.

Thumbnails are generated by a worker, not by the import. Without `compose.workers.yaml` in
`COMPOSE_FILE` and a worker consuming the `default` queue, imported images show no thumbnails and
nothing reports an error — see [Workers](#workers).

## Workers

Append `:compose.workers.yaml` to `COMPOSE_FILE`. The CPU worker `worker-cfi-roi` starts with
the layer and consumes `default`, the thumbnail queue. GPU workers also need a profile in
`COMPOSE_PROFILES`: `gpu-inference`, `gpu-cfi-amd` or `gpu-layer-segmentation`.
`worker-inference` also consumes `default` and `cfi-roi` unless `EYENED_RQ_QUEUES_INFERENCE`
narrows it. With image datasets, uncomment the worker entries in `compose.storage.yaml` — see
"Image datasets" above.

On a separate GPU host:

1. Clone the repository and `cp .env.example .env && chmod 600 .env` in `deploy/`.
2. In that `.env`, set `COMPOSE_FILE=compose.workers.yaml` (add `:compose.storage.yaml` for
   datasets, keeping only the worker entries), the GPU profiles, `EYENED_REDIS_HOST`, `_PORT`
   and `_PASSWORD`, `EYENED_DATABASE_HOST`, `_PORT` and `_PASSWORD`, `EYENED_STORAGE_MOUNTS`,
   and `PLATFORM_STORAGE_PATH`. The last is required: without it results land in a new, empty
   volume.
3. On the platform host, publish MySQL and Redis on an address the GPU host can reach, with a
   site file used instead of `compose.host-ports.yaml` (that one binds loopback only):

   ```yaml
   # compose.site.yaml, appended to COMPOSE_FILE
   services:
     database:
       ports: ["<address>:13306:3306"]
     redis:
       ports: ["<address>:16379:6379"]
   ```

   Docker-published ports bypass ufw, so bind to an address only the GPU host can reach.
4. `docker compose up -d --build` on the GPU host.
