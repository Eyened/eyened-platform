The ORM runs inference through `eorm` commands that write results to the database (`AttributeValue`, `ModelSegmentation`, or patient-level registration JSON). All image-scoped commands share the same **[targeting flags](/eyened-platform/orm/cli#targeting)**.

**Where to run them** depends on the model. The server image does **not** include PyTorch. `cfi-roi` is OpenCV + `retinalysis-fundusprep` and can run in the server container or the slim ROI worker. GPU models need the images under `worker/` — see [Workers and images](#workers-and-images).

## Attribute models (`run-cfi-models`)

Runs **AttributesModel** pipelines — CFI ROI, keypoints, quality scores, etc. Each model:
- Registers as a `Model` row (`ModelName` + `Version`)
- Writes typed values to `AttributeValue`
- Skips images that already have output from **any** version of that model (default)
- Use `--upgrade` to add output for the current model version when only older versions exist (older rows kept; reads prefer the highest `ModelID`)
- Use `--overwrite` to reprocess images that already have a row for the **current** version

Examples:
```bash
eorm run-cfi-models
eorm run-cfi-models --project "My Study"
eorm run-cfi-models --path ids.txt
eorm run-cfi-models -m cfi-keypoints --upgrade
```

With no targeting flags, processes all active ColorFundus images. With no `-m`, all four CFI models run — keypoints, ODFD, and quality need the GPU inference image; `cfi-roi` alone can run in the server container.

`run-models` is a deprecated alias for `run-cfi-models`.

### Model versions

Version strings are derived automatically from installed packages or HuggingFace artifact paths. When the version changes, pipeline init creates a new `AttributesModel`.

| Model | Version source | Example |
|-------|----------------|---------|
| `CFI_ROI` | `retinalysis-fundusprep` package version | `1.1.0` |
| `CFI_Keypoints` | sorted HF artifact paths joined with `+` | `Eyened/vascx/discedge/discedge_july24+Eyened/vascx/fovea/fovea_july24` |
| `CFI_ODFD` | HF artifact path (`repo/subdir/stem`) | `Eyened/vascx/odfd/odfd_march25` |
| `CFI_Quality` | HF artifact path (`repo/subdir/stem`) | `Eyened/vascx/quality/quality` |

Attribute names `CFI_ROI`, `CFI_Keypoints`, `CFI_ODFD`, and `CFI_Quality` are platform-defined — see **[Attributes — reserved names](/eyened-platform/orm/data_model/attributes#reserved-attribute-names-platform-defined)** for API and client consumers.

### Skip and re-run behaviour

| Mode | When an image is processed |
|------|----------------------------|
| **Default** | No `AttributeValue` row exists for this model (any version) |
| **`--upgrade`** | The **current** pipeline version has no row yet; older versions may already exist. New output is stored alongside older rows; reads prefer the newest registration (`ModelID`). |
| **`--failed`** | Within the selected target, only images with a **failed** row for this model (null value columns). Failed rows are retried; succeeded images are skipped. |
| **`--overwrite`** | Always (replaces the current version's row only) |

```bash
eorm run-cfi-models --project "My Study" --failed
eorm run-cfi-models -m cfi-roi --path ids.txt --failed
```

Dependent models (`cfi-keypoints`, `cfi-odfd`, `cfi-quality`) declare `CFI_ROI` as input and resolve it via `resolve_input_attribute_value` — see **[Attributes — selecting which AttributeValue to use](/eyened-platform/orm/data_model/attributes#selecting-which-attributevalue-to-use)**.

Implementation uses optional preprocess → batch → postprocess stages; see `orm/eyened_orm/commands/` in the repository for extending with custom models.

## Segmentation models (`run-segmentation`)

Runs **SegmentationModel** inference into `ModelSegmentation` zarr arrays.

```bash
eorm run-segmentation --project "My Study"
```

## Registration (`run-registration`)

Pairwise enface registration via `eorm run-registration`. Writes transforms to patient **Registration** attributes (not FormAnnotations). See **[Registration](/eyened-platform/orm/registration#batch-inference)** for storage, PublicID rules, and how the viewer merges model output with manual sets.

## ETDRS summary (`run-etdrs-model`)

Computes ETDRS subfield areas from segmentations and keypoint/attribute data — not directly from manual FormAnnotation coordinates unless also present in attributes.

Keypoints (`CFI_Keypoints`) and ODFD (`CFI_ODFD`) inputs are resolved with the same `ModelInputSpec` / highest-`ModelID` selection as CFI attribute pipelines (no manual `--keypoints-model-version` flags).

```bash
eorm run-etdrs-model --project "My Study" -s <segmentation-model-id>
```

See also **[ETDRS Panel](/eyened-platform/client/panels/etdrs)** and **[CLI](/eyened-platform/orm/cli)**.

## Workers and images

| Work | Image | Compose |
|------|--------|---------|
| `cfi-roi`, thumbnails (`default` queue) | `worker/Dockerfile.cfi-roi` (no torch) | `worker/docker-compose.cfi-roi.yml` |
| `cfi-keypoints`, `cfi-odfd`, `cfi-quality` | `worker/Dockerfile.inference` (PyTorch + `retinalysis-inference`) | `worker/docker-compose.inference.yml` |
| `cfi-amd` | `worker/Dockerfile.cfi-amd` | `worker/docker-compose.cfi-amd.yml` |
| `layer-segmentation` | `worker/Dockerfile.layersegmentation` | `worker/docker-compose.layersegmentation.yml` |

Copy `worker/.env.example` to `worker/.env` (Redis, database, `EYENED_STORAGE_ROOT`). If you run both the slim ROI worker and the GPU worker, omit `cfi-roi` (and optionally `default`) from the GPU worker's `EYENED_RQ_WORKER_QUEUES` so each job is handled once.

### Queue via the API (usual production path)

The API only **enqueues**. A worker that listens on the matching queue must be running:

```bash
cd worker
docker compose -f docker-compose.cfi-roi.yml up --build
docker compose -f docker-compose.inference.yml up --build
```

`POST /api/import/run_cfi_models` (and `eorm` enqueue helpers) put `cfi-roi` on the `cfi-roi` queue and the torch models on their own queues. Thumbnail jobs use `default` — see **[Thumbnails](/eyened-platform/thumbnails#worker)**.

### Run `eorm` inside a worker image (one-shot / backfill)

The server container can run `cfi-roi`:

```bash
docker compose run --rm server eorm run-cfi-models -m cfi-roi --project "My Study"
```

GPU CFI models must run in the inference image (torch, CUDA, `retinalysis-inference`):

```bash
cd worker
docker compose -f docker-compose.inference.yml run --rm worker \
  eorm run-cfi-models -m cfi-keypoints --project "My Study"
```

Same pattern for segmentation: `docker compose -f docker-compose.cfi-amd.yml run --rm worker-cfi-amd eorm run-segmentation -m cfi-amd ...` and `docker compose -f docker-compose.layersegmentation.yml run --rm worker-layersegmentation eorm run-segmentation -m layer-segmentation ...`.
