EyeNED is a web platform for browsing, annotating, and managing ophthalmic images. A typical deployment runs several Docker services behind a single nginx entry point; MySQL holds metadata and relationships, while image files live on mounted storage.

## Architecture Overview

![Platform Architecture](../../assets/eyened_platform.png)

**Request flow:** the browser talks to **fileserver** (nginx) on `HTTP_PORT` (set in `deploy/.env`, default `8080`). It proxies `/api/` to the **server** (FastAPI) in both stacks. How `/` is served differs: in production nginx serves the built viewer straight off disk from its own image — there is no client container and no proxy hop; in development the `compose.dev.yaml` layer adds a **client** container running vite, and nginx proxies `/` to it for hot reload. Image bytes and thumbnails are served via nginx internal redirects — the API validates access, then tells nginx which file to send.

## Runtime services

These run from `deploy/compose.yaml`:

| Service | Role |
|---------|------|
| **Fileserver** | nginx reverse proxy; single entry point for UI, API, thumbnails, and image datasets. In production it also *serves* the built viewer off disk |
| **Server** | FastAPI backend — authentication, database access, business logic; enqueues long jobs to Redis |
| **Redis** | Job broker for async work (`EYENED_REDIS_HOST`, `EYENED_REDIS_PORT`, `EYENED_REDIS_PASSWORD`) |

**Client** — the SvelteKit viewer, with WebGL2 rendering for images and segmentations — is a **development-only service**, added by the `compose.dev.yaml` layer to run vite with hot reload. Production has no client container: the same app is built with `@sveltejs/adapter-static` and the resulting static SPA is baked into the fileserver image by `deploy/Dockerfile.fileserver`.

The server also needs `EYENED_API_SECRET_KEY` and the `EYENED_DATABASE_*` variables (see below).

**Worker** is deployed separately (`python -m server.rq_worker`, or the Docker workers in `deploy/compose.workers.yaml`). It uses the same `EYENED_REDIS_*`, `EYENED_DATABASE_*`, and storage env as the server. For the bare process, set `EYENED_RQ_WORKER_QUEUES` to the queues it should consume (include `default` for thumbnail jobs); the Docker workers ignore that variable and set their queues per service instead (`EYENED_RQ_QUEUES_CFI_ROI`, `EYENED_RQ_QUEUES_INFERENCE`, or a queue fixed in the compose file) — see [Thumbnails](/eyened-platform/thumbnails#worker). Without a worker, synchronous CLI paths still work; async API endpoints will queue jobs that never run.

## Database

MySQL stores all structured data: projects, patients, studies, images, annotations, tasks, users, and storage references. It **is** part of the stack, running under the `local-db` profile in `deploy/compose.yaml`. To point the app at an external server instead, remove `local-db` from `COMPOSE_PROFILES` in `deploy/.env` and set:

- `EYENED_DATABASE_HOST`
- `EYENED_DATABASE_PORT`
- `EYENED_DATABASE_USER`
- `EYENED_DATABASE_PASSWORD`
- `EYENED_DATABASE_DATABASE`

For a MySQL shell in the bundled database, `./eyened db-shell` needs no published port and no
separate database browser container — it does not apply once `local-db` is removed.

See [Getting Started](/eyened-platform/getting_started) for setup.

## API concurrency

Route handlers that touch the database run in a threadpool, not on the event loop. One slow query occupies one thread; unrelated requests keep being served.

Six endpoints deliberately stay on the loop. Five of them are the segmentation-data endpoints in `server/routes/segmentations.py`: the zarr store behind them has no lock, so the single-threaded event loop is the only thing serializing concurrent writes to the same array, and moving them into the threadpool loses annotation data. The sixth is the OIDC login callback, which awaits the identity provider, so its two queries stay on the loop as well.

Five settings size that threadpool and the resources behind it:

| Setting | Default | What it caps |
|---------|---------|--------------|
| `EYENED_API_THREADPOOL_LIMIT` | `16` | All sync work offloaded to threads (handlers, dependencies, background tasks), per server process |
| `EYENED_API_POOL_SIZE` | `16` | Pooled connections held open, per server process |
| `EYENED_API_MAX_OVERFLOW` | `4` | Extra connections opened under burst, per server process |
| `EYENED_API_POOL_TIMEOUT` | `5` | Seconds a request waits for a free connection before failing |
| `EYENED_API_PASSWORD_HASH_CONCURRENCY` | `4` | Argon2 password hashes computed at once, per server process |

`EYENED_API_THREADPOOL_LIMIT` must not exceed `EYENED_API_POOL_SIZE` + `EYENED_API_MAX_OVERFLOW`, and a startup validator makes the **server** refuse to boot if it does — what that catches is a grossly undersized pool, the case where threads sit in `pool.connect()` waiting out the timeout. It does not guarantee a checkout never waits: a request holds its connection across several threadpool hops (each sync dependency, the endpoint, response-model validation), so checkouts can exceed the thread count — 20 against 16 threads, measured.

`EYENED_API_POOL_TIMEOUT` is deliberately outside that validated relation: it changes not how many connections exist but how long a request waits for one, turning pool exhaustion into a fast error rather than the 30-second hang SQLAlchemy defaults to — and which the worker, the CLI and the importer still use.

### Password hashing

Argon2 is memory-hard by design: this deployment's parameters cost 64 MiB and roughly 75 ms per hash. While handlers ran on the event loop that cost was serialized by accident — a process computed one hash at a time. The threadpool removes that accident, and `/auth/login` and `/auth/token` require no credentials to reach, so concurrent hashing is capped separately at `EYENED_API_PASSWORD_HASH_CONCURRENCY`.

At the default of `4` a server process holds at most ~256 MiB of Argon2 state, ~1 GiB across `WORKERS=4`. Raising it raises that ceiling proportionally; a value above `EYENED_API_THREADPOOL_LIMIT` can never be reached. A request waiting for a hashing slot still occupies its thread and, on the login path, its pooled connection — a deliberate trade, since exhausting threads or connections fails fast under `EYENED_API_POOL_TIMEOUT` whereas exhausting memory kills the process.

### Connection budget

Every process has its own pool. Connections open lazily, so the numbers below are ceilings, and at peak the database sees the sum:

| Consumer | Processes | Per process | Total |
|----------|-----------|-------------|-------|
| **Server** (`docker/`, gunicorn) | `WORKERS` (default `4`, set in `docker/.env`) | 20 | 80 |
| **Server** (`dev/`, single uvicorn) | 1 | 20 | 20 |
| **Worker** (RQ) | one pool per running job | 15 | varies with concurrency |
| `eorm` CLI / importer | occasional | 15 | varies |

That sum must stay under the database's `max_connections`. MySQL's documented default is `151`, and the `database/` stack does not override it — confirm the value on the target server before raising any of the settings above. Only the server's pool is tuned; the worker, the CLI and the importer all keep the conservative ORM default of 5 + 10.

To shrink the footprint, lower `EYENED_API_POOL_SIZE` and `EYENED_API_THREADPOOL_LIMIT` together — the startup validator rejects a threadpool larger than the pool.

## Storage

Two distinct layers:

**Image datasets** — original DICOM, PNG, etc. Files stay on disk (or object storage mounted into the container). Each file is registered in the database with a `storage_backend_key` and `object_key` (import/API fields; `StorageBackend.Key` and `ImageStorage.ObjectKey` in the database). Add the key and its path to `deploy/storage-mounts.conf` and re-run the entry point (`./eyened install` or `./eyened up`) — the fileserver mount, the nginx `location`, and `EYENED_STORAGE_MOUNTS` are all generated from that one file.

The API itself does **not** read image bytes from disk: `GET /api/images/{image_id}/data` in `server/routes/instances.py` resolves a `StorageRef` and returns an nginx internal redirect (`X-Accel-Redirect`) — nginx reads the file, not the server process. `EYENED_STORAGE_MOUNTS` matters for **ORM-side processes** — GPU workers, notebooks, the thumbnail CLI — that read source pixels directly instead of going through the API.

**Platform storage** — writable data under `EYENED_STORAGE_ROOT`, which is **always** `/storage` inside the containers. It is set there by `deploy/compose.yaml` and is not a `deploy/.env` knob. What *backs* that path is the knob: leave `PLATFORM_STORAGE_PATH` unset and it is this stack's own named volume; set it to an absolute host path and it is a bind mount onto storage you control.

| Path | Contents |
|------|----------|
| `thumbnails/` | JPEG previews (`_144.jpg`, `_540.jpg`); served by nginx at `/thumbnails/` |
| `segmentations.zarr` | Zarr store for user-drawn and model segmentations |

The server container mounts platform storage at `/storage` read-write; the fileserver mounts the *same* storage, also at `/storage`, read-only. It is the nginx configuration, not the mount, that narrows what is reachable: the only location over it is `/thumbnails/`, and that location is `internal`, so it is served solely in response to an `X-Accel-Redirect` from the API.

## Loading data

Images must be on a storage backend **before** import — neither the ORM nor the API uploads files. The primary path is the [ORM importer](/eyened-platform/orm/importer) (Python/CLI, batch CSV, plan → review → apply). A [REST API](/eyened-platform/importing_data#rest-api-alternative) is available for integrations that cannot run the ORM directly.

After import, generate thumbnails separately — see [Thumbnails](/eyened-platform/thumbnails).
