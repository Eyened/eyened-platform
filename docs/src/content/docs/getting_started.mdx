The Eyened platform is a modern web platform for visualization and annotation of ophthalmic images with features like:

- Loading of various image formats including DICOM.
- Convenient system for browsing / filtering loaded studies and images.
- Task system for managing grading tasks.
- Drawing tools for 2D image segmentation of enface images and OCT B-scans
- Images and annotations are rendered in the browser, making it very responsive and easy to set up.
- Authentication system secures the viewer, images, thumbnails and annotations.
- Image enhancements such as CLAHE can be applied on the fly.
- Integrated tools for registration of enface images.
- Automated ETDRS grid placement via AI-based bounds detection and landmark detection (fovea, optic disc) upon insertion of CFI images.

## Quick Setup

Everything the platform needs — viewer, API, database, Redis, and file server — runs from one
Docker stack.

**Prerequisite: Docker, with Compose 2.26 or newer.** That is the whole list — a current Docker
Desktop or Docker Engine install already satisfies it, and `./eyened install` checks before it builds
anything. Supported platforms are Linux and macOS natively, and Windows via WSL2.

1. Clone the repository. Images are built from your checkout, so the checkout *is* the version:

    ```bash
    git clone https://github.com/Eyened/eyened-platform.git
    cd eyened-platform
    ```

2. Run the installer:

    ```bash
    ./eyened install
    ```

    It checks your machine, creates `deploy/.env` with freshly generated secrets, builds the
    images, starts the stack, creates the database schema, seeds the builtin form schemas, and
    prints the URL together with a one-time administrator password. Nothing needs to be edited
    by hand.

3. Open the printed URL and sign in as `admin`.

:::caution
The administrator password is printed **once**. Copy it before closing the terminal. More users
can be created from the user interface, or with `eorm create-user`.
:::

### Day-to-day

Run these from the `deploy/` directory. The installer recorded which layers this stack uses, so
plain Compose commands resolve them with no extra flags:

```bash
cd deploy
docker compose logs -f      # follow logs
docker compose down         # stop
docker compose up -d        # start
```

If your Docker installation has the standalone binary rather than the plugin, use
`docker-compose` instead of `docker compose`. The installer prints whichever one your machine has.

### Upgrading and rolling back

Images are built from your checkout, so moving between versions is a checkout plus a rebuild.
Two things that rebuild does **not** do: it does not migrate an existing database, and it is not
reversible on its own. The steps below handle both.

First record where you are — this is what a rollback returns to, so note it before anything
moves:

```bash
git rev-parse --short HEAD
```

Then work through all four steps, in order.

1. **Back up the database.** Nothing further down does this for you, and a migration cannot be
   reliably undone once it has run:

    ```bash
    ./eyened backup backups/before-upgrade
    ```

    This is a hot backup — the database keeps serving throughout — and writes a raw MySQL
    datadir to `deploy/backups/before-upgrade` (a relative path resolves under `deploy/`; add
    `-t` to also get a single `.tgz`). `deploy/backups/` is gitignored, so step 2 leaves it in
    place. See `deploy/README.md`'s **Backup and rollback** section for the full mechanics.

2. **Move the checkout and rebuild:**

    ```bash
    git pull                    # or: git checkout <branch-or-commit>
    ./eyened install    # rebuilds the images and restarts the stack
    ```

3. **Apply migrations yourself.** `./eyened install` deliberately does not migrate a database that
   already has a schema. It only *reports* which revision that schema is at and, when it is
   behind, prints the command to run — nothing is changed until you run it:

    ```bash
    ./eyened migrate
    # or: cd deploy && docker compose exec -it server sh -c 'cd orm/migrations && alembic upgrade head'
    ```

    Skipping this is the failure this list exists to prevent: new code running against the old
    schema, with nothing saying so.

4. **Verify the schema is where the new code expects it.** The two revision ids must match:

    ```bash
    cd deploy && docker compose exec -T server sh -c 'cd orm/migrations && alembic current && alembic heads'
    ```

    Then open the viewer and sign in.

:::caution
`docker compose up -d` on its own does **not** pick up a new version — it restarts the images you
already built. After moving the checkout, always go through `./eyened install` (or
`docker compose up -d --build`).
:::

To roll back, check out the commit-ish you recorded above and run `./eyened install` again. **A
rollback of the code is not a rollback of the database:** MySQL commits each schema change as it
is applied, so if the upgrade ran `./eyened migrate`, returning to the old code leaves the new
schema in place. That is what the step-1 backup is for — restore it as well:

```bash
./eyened restore backups/before-upgrade
```

`./eyened restore` stops the database, replaces the entire datadir, and starts it again — there
is no undo.

### Adding your first dataset

A fresh install has an empty database, therefore no storage backends and no images — a correct
but blank viewer. To point the platform at a directory of images:

1. Add the dataset to `deploy/storage-mounts.conf`, mapping a key to its path on this machine:

    ```
    my-dataset  /data/my-dataset
    ```

2. Re-run `./eyened install`. From that one file it regenerates the container mounts, the nginx
   routes, and the `EYENED_STORAGE_MOUNTS` setting the ORM reads.

3. Import images with `storage_backend_key: "my-dataset"` — see
   [Importing Data](/eyened-platform/importing_data). The storage backend record is created
   automatically on first import, so there is no separate registration step.

4. Confirm the configuration and the database agree:

    ```bash
    ./eyened check-storage
    ```

:::note
For local development with hot reload, see
[Development Setup](/eyened-platform/guides/development_setup).
:::

:::caution
Set up regular backups for both the database and the storage directories.

| Case | Tool |
|---|---|
| The bundled database — live, fast, byte-exact | `./eyened backup <dir>` / `./eyened restore <dir>` |
| Any database including an external one; portable across MySQL versions | `eorm save_dump` / `eorm load_dump` (a HOST tool — needs `mysqlsh` installed) |

`./eyened backup` never stops the database. See `deploy/README.md`'s **Backup and rollback**
section for both mechanisms in full.
:::

:::tip
**Using the eyened_orm Python package**

Install the ORM for database access and batch imports:

```bash
cd orm
pip install -e .
```

Create an environment file with database credentials. The ORM expects variables with the `EYENED_DATABASE_` prefix (e.g. `EYENED_DATABASE_USER`, `EYENED_DATABASE_PASSWORD`, `EYENED_DATABASE_HOST`, etc.). Load it and connect:

```python
from dotenv import load_dotenv
from eyened_orm import Database

load_dotenv("path/to/your.env")  # or set vars in the environment
database = Database()
session = database.create_session()
```

See [ORM Configuration](/eyened-platform/orm/configuration) for full options.

For batch imports, patching, and audit/undo workflows, see [ORM Importer](/eyened-platform/orm/importer).
:::
