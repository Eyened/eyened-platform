The Eyened platform is a modern web platform for visualization and annotation of ophthalmic images with features like:

- Loading of various image formats including DICOM.
- Convenient system for browsing / filtering loaded studies and images.
- Task system for managing grading tasks.
- Drawing tools for 2D image segmentation of enface images and OCT B-scans
- Images and annotations are rendered in the browser, making it very responsive and easy to set up.
- Authentication system secures the viewer, images, thumbnails and annotations.
- Image enhancements such as CLAHE can be applied on the fly.
- Integrated tools for registration of enface images.
- Automated ETDRS grid placement via AI-based bounds detection and landmark detection (fovea, optic disc) upon insertion of CFI images.

## Quick Setup

These steps install the platform **on your own machine, to try it out**. Everything it needs —
viewer, API, database, Redis and file server — runs from one Docker stack, on the configuration
`.env.example` ships with: the production stack with a bundled database.

To stand the platform up on a server, use
[Production](/eyened-platform/deployment/production) instead. That page is the authoritative
install procedure, and this one does not repeat it.

**Prerequisite: Docker, with Compose 2.26 or newer.** That is the whole list — a current Docker
Desktop or Docker Engine install already satisfies it; older Compose rejects the stack's
`depends_on: required: false`. Supported platforms are Linux and macOS natively, and Windows via WSL2.

For a hot-reload development stack, or for the differences between the stacks, see
[Choosing a stack](/eyened-platform/deployment).

1. Clone the repository. Images are built from your checkout, so the checkout *is* the version:

    ```bash
    git clone https://github.com/Eyened/eyened-platform.git
    cd eyened-platform
    ```

2. Create the configuration:

    ```bash
    cd deploy
    cp .env.example .env && chmod 600 .env
    ```

    `cp` preserves the example file's permissions, which are world-readable, so restrict `.env`
    before you fill it. Fill four secrets with `openssl rand -hex 32`:
    `EYENED_API_SECRET_KEY`, `EYENED_REDIS_PASSWORD`, `MYSQL_ROOT_PASSWORD` and
    `EYENED_DATABASE_PASSWORD`. Compose refuses to start while any of the four is empty. Set
    `EYENED_API_ADMIN_PASSWORD` as well — it is the password you will type at the login screen.

3. Start the stack:

    ```bash
    docker compose up -d --build
    ```

    On the first start the `init` service creates the schema, seeds the builtin form schemas,
    and creates the administrator `admin` (or `EYENED_API_ADMIN_USERNAME`) with the password you
    put in `EYENED_API_ADMIN_PASSWORD` — see [what happens on every
    `up`](/eyened-platform/deployment/operations#what-happens-on-every-up).

4. Open `http://localhost:8080` and sign in as that administrator. `.env.example` ships
   `HTTP_PORT=8080`; if you changed it, use your port.

5. Add the remaining users, and grant each one access. Access comes from project memberships, so
   an account made with `eorm create-user` — or through self-registration in the user interface —
   logs in and sees **nothing** until it is granted a role in an **existing** project. There is no
   command to create an empty one; a `Project` row is created as a side effect of importing data
   into it — see **[Importing data](/eyened-platform/importing_data)**. Assuming a project named
   `AMD-Study` already exists:

    ```bash
    cd deploy
    docker compose exec server eorm create-user --username alice --password '...'
    docker compose exec server eorm grant --user alice --project "AMD-Study" --role grader
    ```

    Roles are `read_only`, `grader`, and `project_admin`. Grants take effect on the user's next
    request — no re-login. Another administrator needs `eorm set-admin --user <username> --on`
    instead — `create-user` cannot make one. `init-admin` also promotes an existing account, but
    it prompts for (and may overwrite) that account's password, which is why `set-admin` is the
    right tool for one that already has the login it should keep. See **[Access
    control](/eyened-platform/guides/access_control)** for the model and **[CLI
    reference](/eyened-platform/orm/cli#users-and-access)** for every command.

### Where to go next

- **Running the stack day to day** — start, stop, follow logs, apply migrations, open a MySQL
  shell: [Operations](/eyened-platform/deployment/operations#day-to-day). Run everything from the
  `deploy/` directory; `.env` records which layers the stack uses.
- **Upgrading and rolling back** — images are built from your checkout, so an upgrade is a
  checkout plus a rebuild, and starting the stack never migrates an existing schema: [Upgrading
  and rolling back](/eyened-platform/deployment/operations#upgrading-and-rolling-back). Upgrading
  from a version that predates `deploy/`: read the **Deployment** section of the [release
  notes](/eyened-platform/release_notes) first.
- **Your first dataset** — a fresh install has an empty database, therefore no storage backends
  and no images: a correct but blank viewer. Mounting a directory of images is four steps, one of
  which is easy to miss if you also run workers: [Image
  datasets](/eyened-platform/deployment/production#image-datasets). Then import with
  `storage_backend_key: "<key>"` — see [Importing data](/eyened-platform/importing_data). The
  storage backend record is created automatically on first import, so there is no separate
  registration step.
- **Thumbnails** need a running worker. Without one, imported images show no thumbnails and
  nothing reports an error — see [Workers](/eyened-platform/deployment/production#workers).
- **On a server** — [Production](/eyened-platform/deployment/production) covers TLS termination,
  an external database, sizing, and what to check before you go live.
- **Local development with hot reload** —
  [Development](/eyened-platform/deployment/development).

:::caution
Set up regular backups for both the database and the storage directories.

See [Routine backups](/eyened-platform/deployment/operations#routine-backups): what to back up,
XtraBackup for a hot backup of the bundled database, and `mysqldump` for a portable one.
:::

:::tip
**Using the eyened_orm Python package**

Install the ORM for database access and batch imports:

```bash
cd orm
pip install -e .
```

Create an environment file with database credentials. The ORM expects variables with the `EYENED_DATABASE_` prefix (e.g. `EYENED_DATABASE_USER`, `EYENED_DATABASE_PASSWORD`, `EYENED_DATABASE_HOST`, etc.). Load it and connect:

```python
from dotenv import load_dotenv
from eyened_orm import Database

load_dotenv("path/to/your.env")  # or set vars in the environment
database = Database()
session = database.create_session()
```

See [ORM Configuration](/eyened-platform/orm/configuration) for full options.

For batch imports, patching, and audit/undo workflows, see [ORM Importer](/eyened-platform/orm/importer).
:::
