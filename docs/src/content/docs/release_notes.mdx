## Unreleased

Changes merged since v2026.09.0. This section is renamed to the version heading when the next release is cut. Add an entry here in the same pull request that changes behaviour — reconstructing it at release time is how things get missed.

### Deployment

The three compose stacks are replaced by one. Everything in this section is about moving from
v2026.09.0 — `dev/` plus `database/` for developers, `docker/` for site deployments — to
`deploy/`. Do the two "before you pull" items first.

**The bundled database starts empty**, and following this section does not bring existing data
across. Moving an existing database into `deploy/` is a separate procedure, documented in
[Moving an existing database into this stack](/eyened-platform/deployment/operations#moving-an-existing-database-into-this-stack). It is an **outage**: the
old database is stopped cold for the copy and stays down until the new stack serves, so plan a
window. A site running against an external database is the exception — it keeps using that
database.

- **Before you pull: take a database backup with the tooling you have now, and keep the old
  checkout.** Nothing in `deploy/` can take this backup; `deploy/` does not exist in the version
  you are on. For the bundled `database/` stack that is `./save_dump.sh <dir>`, run from
  `database/`. Two things about it: it authenticates as the `EYENED_DATABASE_USER` in
  `database/.env`, which defaults to the application account `eyened` and has no `BACKUP_ADMIN`
  privilege, so give it an account that has one; and it does `rm -rf` on `<dir>` without asking.
  Rolling back means rolling code and data back together — check out the old revision and restore
  with that checkout's `database/load_dump.sh`.
- **Before you pull: bring the old stacks down.** The pull deletes `dev/`, `docker/` and
  `database/`, and takes their compose files with them, so afterwards `cd dev && docker compose
  down` fails with "no configuration file" and the legacy volumes — `db_data` from the `database`
  stack, `client_node_modules` from the `dev` one — have nothing left to remove them. Nothing in
  `deploy/` touches either. If you have already pulled, Compose can still address a project by
  name with no file present (`docker compose -p <project> ps` lists it), or recover the file
  itself with `git show <ref-before-this-release>:dev/docker-compose.yml`. Your `.env` files are
  untracked, so they survive the pull in otherwise empty directories; nothing reads them any more.
- **One Docker stack.** `dev/`, `docker/` and `database/` are replaced by a single `deploy/`
  directory run with plain `docker compose`: `deploy/.env` picks the development or production
  layers and whether the bundled database runs, and a one-shot `init` service creates and seeds an
  empty database and the first administrator before the server starts. It reports pending
  migrations on an existing database but does not apply them. Docker is the only prerequisite. The
  database is part of the stack rather than a second compose project to start first. Full
  reference: [Deployment](/eyened-platform/deployment).
- **One env file.** `deploy/.env`, copied from `deploy/.env.example`, with the secrets filled by
  hand. `dev/.env`, `docker/.env`, `database/.env` and `worker/.env` are not read.
- **Breaking: environment variables renamed.** `DEV_NGINX_PORT` → `HTTP_PORT`, the `docker/`
  stack's `PORT` → `HTTP_PORT`, `DEV_PUBLIC_HOST` → `PUBLIC_HOST`, `DEV_KEYCLOAK_PORT` →
  `KEYCLOAK_PORT`. One stack now serves development and production, so the `DEV_` prefix was
  misleading. The `PORT` rename changes the value with it: the default is `8080`, not `80`, and
  `deploy/.env.example` sets it, so a site that served on `:80` moves to `:8080` unless you set
  `HTTP_PORT=80` yourself — check whatever is in front of it (reverse proxy, firewall rule).
  `EYENED_DATABASE_PORT` keeps its name but not always its meaning: the `database` stack published
  MySQL on the host at that port, while `docker/` already used it as the server's connect port. It
  is now always the connect port — so a value carried from the `database` stack points the server
  at nothing, while one carried from `docker/` is still correct.
- **Breaking: `EYENED_STORAGE_ROOT` is no longer an operator setting.** The container path is
  pinned to `/storage`. Platform storage is placed on the host with `PLATFORM_STORAGE_PATH`, and
  image datasets mount at `/data/<key>` via `deploy/compose.storage.yaml`, listed in
  `EYENED_STORAGE_MOUNTS`. `EYENED_STORAGE_ROOT` in `deploy/.env` is ignored.
- **Breaking: the `Makefile` is gone.** Its three targets — `gen-openapi`, `gen-types`,
  `gen-client-types` — are now the single command `npm run gen:types` in `client/`. `make` is not a
  prerequisite.
- **Breaking: Docker Compose 2.26 or newer is now required.** The `init` service's dependency on
  the bundled database uses `depends_on: required: false`, which is what lets the same stack run
  with a bundled or an external database. Older Compose either rejects it or silently drops the
  dependency, which makes `init` race MySQL and fail on first boot.
- **Breaking: MySQL and Redis no longer publish host ports.** Both used to be published on every
  interface — MySQL by the `database` stack, Redis by `dev/` and `docker/`. Neither is published
  by default now: append `:compose.host-ports.yaml` to `COMPOSE_FILE` in `deploy/.env` and set
  `DB_PUBLISH_PORT` / `REDIS_PUBLISH_PORT`, which bind to loopback only. An external RQ worker
  configured from `worker/.env` can no longer reach Redis, so jobs are enqueued and never run with
  nothing reporting a problem; host-side `eorm`, alembic and database GUIs lose `localhost:3306`
  the same way.
- **Adminer is gone.** It used to start automatically with the `database` stack, on
  `EYENED_ADMINER_PORT` (default `8080`); nothing in `deploy/` starts it. For a MySQL shell, see
  [Day-to-day](/eyened-platform/deployment/operations#day-to-day). For a GUI, append `:compose.host-ports.yaml` to `COMPOSE_FILE`
  in `deploy/.env` to publish MySQL on a loopback host port, then point a locally installed client
  (DBeaver, TablePlus, etc.) at it.
- **Keycloak is part of the stack.** `dev/keycloak/` moved to `deploy/keycloak/` and the
  standalone `docker-compose.keycloak.yml` overlay it was layered with is gone: enable OIDC by
  appending `:compose.oidc.yaml` to `COMPOSE_FILE` in `deploy/.env`. Existing OIDC setups must
  also rename `DEV_KEYCLOAK_PORT` to `KEYCLOAK_PORT` — see the renames above — and set the
  `EYENED_OIDC_*` client settings, which `deploy/.env.example` now carries.
- **`database/save_dump.sh` and `load_dump.sh` are gone.** The bundled database is backed up with
  XtraBackup or `mysqldump` through `docker compose`; see [Backup and
  restore](/eyened-platform/deployment/operations#backup-and-restore). `eorm save-dump` / `eorm load-dump` are unchanged.
- **`worker/`'s compose files and `.env` are gone.** The four `worker/docker-compose.*.yml` files
  and `worker/.env*` are replaced by `deploy/compose.workers.yaml`, which reads `deploy/.env` —
  there is no separate worker env file any more. `EYENED_WORKER_DIR` is renamed
  `EYENED_DEPLOY_DIR`; the old name is ignored, with a warning. The Docker workers no longer take
  `EYENED_RQ_WORKER_QUEUES` from the env file — set `EYENED_RQ_QUEUES_CFI_ROI` or
  `EYENED_RQ_QUEUES_INFERENCE` instead. See `worker/README.md`.
- **After moving the checkout, rebuild.** Images are built from your checkout, so a plain
  `docker compose up -d` reuses the images you already have and picks up nothing. Use
  `docker compose up -d --build`.
- **The production frontend is served by nginx, not by Node.** The app is a static SPA
  (`adapter-static`), so production no longer runs `vite preview` behind a proxy — the built
  output is baked into the fileserver image. One fewer container, one fewer proxy hop, and no
  Node process in production. Development is unchanged: vite with hot reload.
- **MySQL is pinned to 8.4.11 LTS** (was 8.0.27; MySQL 8.0 is out of support). The first
  start on an existing 8.0 datadir upgrades it in place, and 8.0 cannot open it again.
- **Storage mounts need no nginx entry.** `deploy/compose.storage.yaml` mounts each dataset at
  `/data/<key>`, and nginx serves every dataset from one internal `/data/` location.
  `EYENED_STORAGE_MOUNTS` in `deploy/.env` must list the same keys: a missing key makes Python-side
  pixel reads (thumbnail regeneration, inference, reports) fail while the viewer still works.
- **No placeholder secrets.** `docker/.env.example` and `database/.env.example` shipped
  `change_me` values that kept working if you never changed them. `deploy/.env.example` ships
  them empty, to be filled with `openssl rand -hex 32`, and `docker compose up` refuses to start
  until they are set (the admin password is checked by `init`, on an empty database). That is
  deliberate, not a regression.
- **Container logs are capped** at 10 MB × 3 files per service, so a long-running install cannot
  fill the disk.
- **`eorm` confirmation prompts on database state.** `initialize-database` and `load-dump` ask
  for the typed confirmation code only when the target database contains tables, which is what
  makes an unattended first-run bootstrap possible. A populated database is still gated.

## v2026.09.0

Per-project access control is now enforced, tasks declare the projects they span, and the
API serves requests concurrently for the first time. This release is also relicensed
under AGPL-3.0.

**This release cannot be deployed as a rolling upgrade.** It needs a planned outage of
about 15 minutes at development scale, backup included. Follow [Upgrading to v2026.09.0](/eyened-platform/guides/upgrading_to_v2026_09_0/).

### Highlights

- **Per-project access control is enforced** (#195). v2026.08.0 shipped the service layer
  as preparation; permissions are now checked on every request. Each project membership
  carries one of `read_only`, `grader`, or `project_admin`; platform administrators are
  data superusers. Scope is re-read from the database per request, so grants and
  revocations take effect on the user's next request without re-login. There is no
  feature flag — rollback is redeploying the previous server.
- **Tasks declare their projects** (#222). A task's project span used to be derived by
  walking every image up to its patient. It is now declared in a new `TaskProject` table,
  which is authoritative for visibility. Existing tasks are backfilled automatically.
- **The API serves requests concurrently** (#219). 69 route handlers ran synchronous
  database calls on the event loop, so each worker served one request at a time and one
  slow query froze the rest (#61). They now run in a threadpool.
- **The tasks page is fast** (#212). `GET /api/task` went from ~15.0 s to ~2.0 s of SQL.
- **Task status in the grading window** (#225). The full-screen task overlay is replaced
  by a collapsible column beside the top-row thumbnails, carrying set navigation, subtask
  status buttons, comments, and a link to the task overview.
- **Tasks can drive the viewer layout** (#178). `TaskDefinition.TaskConfig` can hide
  builtin side panels, prepend a `quick-form` panel, configure the task panel, and set
  point-marker appearance.
- **Claim subtasks** (#178). Task pages gain Claim / Unclaim per row,
  claim-all-unassigned, an assignee column, and status/assignee filters. Editing comments
  or creating an annotation auto-claims an unassigned subtask; it never steals an
  assigned one.
- **DICOM export** (#214). A new `eyened_orm.export` module writes selected images as
  Secondary Capture DICOM, with optional pseudonymisation and per-patient date offsets.
- **Warp segmentations into image space** (#229). `SegmentationBase.warp_to_image()`
  projects a 2D mask back into the original image's pixel space.
- **Relicensed under AGPL-3.0** (#215), from GPL-3.0.
- **One Alembic baseline** (#216). The 24 legacy revisions are squashed into
  `orm_baseline`.

### Changed behaviour

Things that worked one way in v2026.08.0 and work differently now.

**Viewer**

- **Masking is on by default** (#211). A grader segmentation with a reference mask now
  renders intersected with it; previously it rendered unmasked. A new Intersection button
  sits next to the eye icon in the Segmentation panel row, and the choice is remembered
  per image.
- **Linking the cursor from a thumbnail needs Shift** (#224, #227). Hovering a main viewer
  always moves the linked cursor and OCT B-scan, including while Shift-panning. Hovering a
  top-row thumbnail does nothing unless Shift is held. Neither updates while a mouse
  button is down.
- The task overlay is gone, replaced by the task panel described above (#225).

**Permissions**

- Reading anything outside your projects returns **404**, not 403 — a 403 would confirm
  the row exists.
- **Modifying another user's annotation is refused** (403), administrators included.
- **Deleting another user's annotation, or deleting a populated task, requires project
  admin.**
- **Adding an image from a project a task does not declare is refused** with 409
  `image_outside_task_declaration`. Extend the task's declaration first.
- **Removing an image no longer widens access.** "Unlink the image to restore access" used
  to work and now silently does nothing. Use `eorm grant-for-task` instead.
- A task is visible only to users holding **every** project in its declaration, so a broad
  declaration hides it from everyone else from the moment it is created. Declarations
  cannot be narrowed in this release.

**API**

- **`GET /api/task` no longer returns project spans by default.** `projects` is `null`
  unless you pass `?include_projects=true`; `null` means "not requested", not "spans
  nothing". `GET /api/task/{id}` still populates it.
- **Two unscoped routes were removed**: `GET /api/instances/images/{...}` and
  `GET /api/instances/thumbnails/{...}`. They authenticated but did not scope, so they
  served other projects' pixels. Use `GET /images/{id}/data` and
  `GET /images/{id}/thumbnail`.
- **`POST /task` requires a non-empty `projects` list**, and `grader` in every project in
  it.
- New: `GET /task/{id}/subtask-assignees`; `unassigned` and `creator_id` filters on
  `GET /task/{id}/subtasks`; `claim` on `PATCH /subtasks/{id}`, which returns 409
  `subtask_already_claimed` if someone else holds it.
- `GET /import/status/{task_id}` now requires authentication.

**CLI**

- **`eorm initialize-database` runs the migration trail to head** instead of creating
  tables and stamping. The database must already exist; `--recreate` drops and creates it
  first.
- `eorm create-user` exits non-zero on a duplicate username instead of printing and
  exiting 0.
- New administration commands: `init-admin`, `grant`, `revoke`, `grant-for-task`,
  `grant-all`, `set-admin`, `set-password`, `deactivate`, `reactivate`,
  `check-declarations`, `check-dangling-references`.

### Bug fixes

- Fundus/OCT registrations did not load: device `PhotoLocators` were being dropped from
  `ImageGET.attrs` (#227).
- Deleting a tag that is still applied returns 409 instead of 500, and the database
  refuses the delete outright (#195).
- `POST /auth/register` with a taken username returns 409 instead of 500 (#195).
- Form saves that fail now raise a toast instead of sticking on "saving"; debounced saves
  flush when the window closes; blank B-scan indices are rejected (#178).
- ETDRS ring masks are computed as independent distance bands, so building the 3 mm grid
  no longer materialises all three rings (#223). Measured areas and counts are unchanged.
- `alembic check` no longer reports drift on sites upgraded through the legacy trail:
  `AnnotationData.DateModified` gets its missing `DEFAULT CURRENT_TIMESTAMP`. Existing values are unchanged.

### Upgrade notes

**Not a rolling upgrade.** Follow **[Upgrading to v2026.09.0](/eyened-platform/guides/upgrading_to_v2026_09_0/)**. In summary:

- Outage: about 15 minutes at development scale, backup included. The API, the RQ workers and all imports stay stopped.
- Finish the legacy migrations from an image built at `6c675e5`, stamp `orm_baseline`, then apply six revisions with the new image.
- Before users return: `eorm init-admin` with a password, `eorm grant-all`, then review the grant.
- Rebuild every image containing `eyened_orm` (the server and every worker): this release adds `passlib` and `argon2-cffi`.
- Connection budget: each API process can open `EYENED_API_POOL_SIZE + EYENED_API_MAX_OVERFLOW` = 20 connections; the server refuses to boot if `EYENED_API_THREADPOOL_LIMIT` exceeds that.
- Keep `EYENED_API_PUBLIC_AUTH_DISABLED=false` in production: the dev bypass promotes its account to administrator.

### New settings

| Setting | Default | Purpose |
|---|---|---|
| `EYENED_API_ADMIN_USERNAME` | `admin` | Names the account `eorm init-admin` bootstraps |
| `EYENED_API_ADMIN_PASSWORD` | — | Read by `eorm init-admin`, not by the server |
| `EYENED_API_THREADPOOL_LIMIT` | 16 | Threadpool size for synchronous route handlers |
| `EYENED_API_POOL_SIZE` | 16 | SQLAlchemy pool size (API only) |
| `EYENED_API_MAX_OVERFLOW` | 4 | SQLAlchemy overflow connections |
| `EYENED_API_POOL_TIMEOUT` | 5 s | Wait before a connection checkout fails |
| `EYENED_API_PASSWORD_HASH_CONCURRENCY` | 4 | Caps concurrent Argon2 hashes on the login routes |
| `EYENED_ALEMBIC_ASSUME_YES` | unset | Skips Alembic's confirmation prompt for non-interactive runs |
| `EYENED_DATABASE_BUFFER_POOL_SIZE` | — | Sets `innodb_buffer_pool_size`; takes effect when the container is recreated |

## v2026.08.0

This release focuses on viewer persistence and enface overlays, a service-layer cutover with an audit log (groundwork for RBAC), and a rewrite of CFI model inference. Version numbers follow calendar versioning (`YYYY.MM.MICRO`).

### Highlights

- **Viewer bookmarks:** open viewers and B-scan indices persist in the URL (`v=`) and localStorage (#198).
- **Enface on registered images:** overlays follow GPU registration hops; photolocator hit testing covers raster, radial, and circular locators (#177, #194).
- **Server service layer:** FastAPI routes go through repositories and services; mutations write an append-only `AuditLog`. This is preparation for RBAC, not a permission-model change for operators (#134, #139, #145, #165, #171).
- **CFI inference:** `eorm run-cfi-models` replaces the previous CFI writers, with model versions, input specs, and more robust batching (#158).
- **CI:** client and server test/lint gates on `development` and `main`.
- **CODEOWNERS:** repository-wide review by `@Eyened/platform-core`.

### Bug fixes

**Viewer**

- Large DICOM volumes and IR/OCT stretch (#196, #173).
- Patient registration on task viewer (#144).
- CirclePhotoLocator crash (#157).
- Multiclass erode/dilate (#131).
- Copy public ID from browser and viewer thumbnails (#140, #143).

**ORM / server**

- PNG series path resolution (#191).
- CFI inference filtering, thumbnails, lock/deadlock replay (#158).
- Removed unused `mysql-connector-python` (#199).
- Registration processing exception handling (#147).

### Upgrade notes

1. Run database migrations before starting the new server containers (`AuditLog` table).
2. Reinstall `eyened_orm` after pulling.
3. Use `eorm run-cfi-models` instead of the removed legacy CFI writers.
4. Do not depend on `mysql-connector-python`.
5. Authentication (password + optional OIDC) is unchanged from v2026.07.0.

## v2026.07.0

This release focuses on making EyeNED easier to run in real environments and more pleasant for day-to-day annotation work. Version numbers now follow calendar versioning (`YYYY.MM.MICRO`).

### Highlights

- **Single sign-on support:** EyeNED can authenticate with OpenID Connect providers, including secure ID-token validation, nonce/CSRF checks, optional automatic account creation, and a local Keycloak setup for development.
- **More useful viewer and task UI:** embeddable browser widget, global help panel, per-panel help overlays, browser overlay fixes, smoother task/search performance, pending-segmentation unload checks, and small layout improvements.
- **EyeNED ORM:** the ORM can now load images and segmentations either through the API or a local file-storage adapter.
- **Better segmentation workflows:** the viewer has a unified segmentation creation flow, region tools, feature pipette support, multiclass/multilabel opacity controls, B-scan link scrolling, probability-mask area calculation fixes, Ctrl-Z undo support.
- **Safer, clearer imports:** the ORM importer now plans changes before applying them, supports CSV and JSON audit/undo workflows, handles idempotent re-runs, documents how patient/study/series/image rows are matched, and reports clearer errors when required parent records cannot be resolved.
- **Unified `eorm` CLI targeting:** shared `--path`, `--project`, `--patient`, `--exclude`, and `--modality` flags across inference and maintenance commands. See [CLI](/eyened-platform/orm/cli).
- **Deployment and developer setup updates:** database, Docker, Redis/RQ worker, Keycloak, and storage instructions have been refreshed. Database setup is extracted into a new `database/` subdirectory with a standalone stack, including tools for creating and loading database dumps.
- **Database setup improvements:** `eorm initialize-database` creates tables and stamps the current Alembic revision so later `alembic upgrade head` runs apply only new migrations.
- **Thumbnail generation is centralized:** imports no longer hide thumbnail work. Use `eorm update-thumbnails`, `PostImport`, or the async import API endpoints depending on where the work should run.
- **ETDRS and form schemas:** builtin viewer FormSchemas (ETDRS grid, registration) can be seeded with `eorm seed-form-schemas`. See the [ETDRS Panel](/eyened-platform/client/panels/etdrs) and [Form Schemas](/eyened-platform/orm/form_schemas) docs.
- **Registration model versioning:** each package version gets its own `Model` row; patient attributes preserve provenance per model version; viewer crosshair linking works across registration graph versions.

### Bug fixes

**Viewer and annotation**

- Segmentations and registration graphs load correctly when adding images dynamically to the viewer (#104).
- Browser overlay shows loaded images again.
- Segmentation area measurement works correctly for probability masks.
- Segmentations with a sparse axis render and measure correctly.
- Composite features can be created from a list of existing features.
- B-scan numbers update dynamically when scrolling linked OCT scans.
- ETDRS overlay renders correctly on enface OCT images.
- Subtask row index stays correct when filtering tasks (#69).
- Task overlay state buttons update reactively.
- Search fields pre-fill from URL parameters (#58).

**Import and data**

- Using random `Public ID`s for images instead of database primary keys.
- DICOM RGB images load correctly during preprocessing.
- DICOM parser handles edge cases more reliably.
- Image importer API mismatches corrected.

**Server and CLI**

- Nullable enum columns no longer cause 500 errors (#63).
- Concurrent API requests handled reliably (#61).
- Slow signatures endpoint improved.
- Worker Redis DNS resolution fixed.

### Upgrade notes

1. Run database migrations before starting the new server containers.
2. On fresh deployments, run `eorm seed-form-schemas` after `eorm initialize-database` (or pass `--seed-form-schemas` to combine both steps).
3. Review authentication settings before deployment. Password login remains enabled by default; OIDC is opt-in via `EYENED_API_AUTH_OIDC_ENABLED=true`.
4. Ensure at least one RQ worker listens to the `default` queue if you use async thumbnail jobs.
5. If you install `eyened_orm` directly, reinstall it after pulling this release so the ORM-owned dependencies, including `zarr`, are available.
6. **Patient attributes API change:** `GET /patients/{id}` now returns each attribute as a list of `{ value, model }` entries so provenance per model version is preserved.
